# TemelashCard data model

Source of truth: `prisma/schema.prisma` plus the hand-written SQL in
`prisma/migrations/*_integrity_constraints/migration.sql`.

## Conventions

- UUID primary keys generated by PostgreSQL (`gen_random_uuid()`); every timestamp is `timestamptz` (UTC).
- Tables and columns are `snake_case`; Prisma models are `PascalCase`/`camelCase` via `@@map`/`@map`.
- **Nothing financial is stored.** No amounts, prices, revenue, order values, invoices, subscriptions or
  payment methods. A test scans the catalog for such column names.
- Foreign keys are `ON DELETE RESTRICT` everywhere. History survives; things are _deactivated_, never deleted.

## Entity relationships

```
PlatformUser ──< StaffMembership >── Role >──< Permission        (via role_permissions)
                     │  └──< StaffBranchAssignment >── Branch
Merchant ─┬─ MerchantSettings (1:1)
          ├──< Branch
          ├──< StaffMembership
          ├──< Customer ──< CustomerConsent (append-only)
          └──< LoyaltyProgram ──< RewardDefinition
                     │
Customer ──< CustomerMembership >── LoyaltyProgram          (unique per customer+program)
                     │
                     ├──< WalletPass            (one per provider: APPLE | GOOGLE | WEB)
                     ├──< StampEvent            (append-only)  ── Branch, StaffMembership
                     ├──< RewardUnlock          (append-only)  ── triggered by one StampEvent
                     ├──< RedemptionEvent       (append-only)  ── RewardUnlock, Branch, StaffMembership
                     └──< ReversalEvent         (append-only)  ── one StampEvent XOR one RedemptionEvent

IdempotencyRecord ── StaffMembership      AuditEvent (append-only)      OutboxJob
```

`Role` and `Permission` are the only global (non-tenant) catalogs; `PlatformUser` is global because one
login can exist before it joins a merchant. Everything else carries `merchant_id`.

## Tenant isolation in the schema

Child rows reference parents through **composite foreign keys that include `merchant_id`**, for example
`stamp_events (branch_id, merchant_id) → branches (id, merchant_id)`. A row therefore cannot reference a
parent that belongs to another merchant, even if application code is wrong. The same phone number may exist
at two merchants as two unrelated `customers` rows (`UNIQUE (merchant_id, phone_e164)`), and nothing in the
data model links them.

## Invariants (and what enforces them)

| Invariant                                                                                                             | Enforced by                                                                                                                                       |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| No cross-tenant references                                                                                            | Composite FKs on `merchant_id`                                                                                                                    |
| Phone numbers are Ethiopian E.164 `+251` + 9 digits                                                                   | CHECK on customers, branches, merchant_settings; `normalizeEthiopianPhone()` in app code                                                          |
| One customer record per merchant+phone                                                                                | `UNIQUE (merchant_id, phone_e164)`                                                                                                                |
| One membership per customer and program                                                                               | `UNIQUE (customer_id, program_id)`                                                                                                                |
| One default ACTIVE program per merchant (MVP)                                                                         | Partial unique index `loyalty_programs_one_default_active`                                                                                        |
| One ACTIVE reward definition per program (MVP)                                                                        | Partial unique index `reward_definitions_one_active_per_program`                                                                                  |
| `stamps_required` 1–1000, `cooldown_minutes` ≥ 0, brand color `#RRGGBB`                                               | CHECK constraints                                                                                                                                 |
| Stamp, unlock, redemption, reversal, audit and consent rows are never changed or removed                              | `forbid_mutation()` triggers on UPDATE, DELETE and TRUNCATE                                                                                       |
| Corrections are compensating events                                                                                   | `reversal_events`: exactly one target (CHECK), reason ≥ 3 chars (CHECK), each event reversible once (unique), same membership as target (trigger) |
| An unlock is triggered by a stamp of the same membership; a redemption matches its unlock's membership                | Triggers                                                                                                                                          |
| An unlock can be redeemed once at a time                                                                              | `UNIQUE (reward_unlock_id, attempt_number)`; attempt N+1 is only possible after attempt N is reversed (application logic under row lock)          |
| A scanner retry cannot create a second event                                                                          | `UNIQUE (staff_membership_id, idempotency_key)` on stamps, redemptions and reversals; `idempotency_records` stores the original response          |
| Platform administrators have no merchant access; merchant memberships need a MERCHANT_USER and a MERCHANT-scoped role | Trigger `enforce_staff_membership_scopes`                                                                                                         |
| Deactivation is consistent (`status` ⇔ `deactivated_at`)                                                              | CHECK constraints                                                                                                                                 |
| Anonymized customers carry no phone number or name                                                                    | CHECK `customers_anonymized_has_no_pii`                                                                                                           |
| Raw scan tokens, passwords and Apple auth tokens are never stored                                                     | Only `token_hash` / `password_hash` / `auth_token_hash` columns exist                                                                             |

## Derived, not stored

- **Stamp balance / progress**: `count(stamp_events) − count(reversed stamps)` for the membership, modulo
  the program threshold. A cached counter will be added only if measurements justify it.
- **Reward status**: `available` (unlock exists, no active redemption, not expired), `redeemed` (a redemption
  exists whose reversal does not), `expired` (`expires_at` passed), `reversed` (its triggering stamp was
  reversed). No mutable status column can drift from the ledger.
- **Current consent**: the latest `customer_consents` row per customer and consent type.

## Bilingual content

English is required; Amharic is optional and stored in sibling `*_am` columns (`name_am`, `terms_am`,
`description_am`). The API falls back to English when Amharic is missing. Preferred language is stored on
users and customers (`EN`/`AM`).

## Added after the first schema

- `refresh_tokens` (hash only, family id for theft detection) and lockout fields on `platform_users`.
- `staff_invitations` (hash only, single use, 7-day expiry).

- `wallet_passes`: `barcode_hash` / `barcode_version` (per-pass revocable barcode), `last_synced_version`; one live pass per membership and provider (partial unique index). `apple_device_registrations` for the Apple web service.

- `fraud_flags` (one row per indicator, subject and UTC window; ids and counts only), `idempotency_records.membership_id` (so anonymization can purge cached answers), `merchant_settings.fraud_thresholds` / `retention_policy`. See [audit-fraud-privacy.md](audit-fraud-privacy.md).

## Not yet modeled

- Analytics summary tables: none by design. Metrics are computed from the ledger with indexes (see [analytics.md](analytics.md)).

## Seed

`npm run db:seed` creates reference data (roles, permissions) and, outside production, one platform admin,
one sample merchant with two branches, an owner, two branch staff, one active stamp program with a reward,
and two customers. Credentials and test scan tokens are written to the gitignored `.seed-output.json`.
Set `SEED_PASSWORD` to choose the shared development password. In production only reference data is seeded.
