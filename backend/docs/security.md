## Review findings from the production-readiness pass

Fixed in this pass:

1. **Module cycle** `merchants → audit → merchants` (it surfaced as an import-order-dependent start-up failure). The audit read side now lives in `audit-viewer`; an architecture test fails the build on any future cycle or boundary breach.
2. **`413`/malformed body returned `500`** for body-parser errors. They now return the standard envelope with `PAYLOAD_TOO_LARGE`/`VALIDATION_FAILED`.
3. **No way to create the first administrator or merchant in production** (only the development seed could). Added `npm run bootstrap` (see [operations.md](operations.md)).
4. **`nest build` could exit 0 without emitting `dist/`** when a stale incremental build file existed. The build config is now non-incremental.
5. **Proxy awareness**: rate limiting and logs saw the proxy's address. `TRUST_PROXY` now configures Express.
6. **Placeholder secrets could reach production.** Start-up validation now rejects them.
7. Defence in depth: the web-pass lookup is now also scoped by merchant.

Reviewed and accepted (by design):

- A few internal operations address a wallet pass or device registration by its primary-key UUID without a merchant filter (pass sync after an outbox job, Apple's protocol endpoints). The ids are unguessable, come from already-authorised contexts, and Apple's endpoints additionally require the pass's own authentication token. The Apple "serials for device" call is unauthenticated by Apple's specification and returns only opaque pass serials.
- The token lookup for a scan is the one lookup that starts from the credential rather than the tenant; the scanner then re-checks the tenant.

## Row-Level Security (open decision)

Tenant isolation currently has two layers inside the application and schema: tenant-scoped repositories and composite foreign keys, both covered by tests. PostgreSQL Row-Level Security (RLS) would add a third layer that protects even against a missing `WHERE merchant_id`. It was **not** enabled because it needs a non-owner application role, a per-request `SET LOCAL app.merchant_id` inside every transaction (including the outbox worker, schedulers and Apple endpoints, which have no signed-in merchant), and policy tests. Recommended approach if you want it: create `app_user` without `BYPASSRLS`, add `USING (merchant_id = current_setting('app.merchant_id')::uuid)` policies to tenant tables, extend `TransactionManager.run` to set the setting, and give background jobs an explicit system role. Say the word and it can be done as a separate, reversible migration.

## Known weaknesses to plan for

- **Rate-limit counters are per process.** Several instances multiply the budget; use a shared store (Redis) before scaling out.
- **The global per-IP budget (100/min) is shared by every scanner behind one shop's router.** Raise `RATE_LIMIT_MAX` or key scanner traffic by staff account if a busy store hits it.
- **No password change, reset or e-mail verification endpoints yet.** A forgotten password needs an administrator to re-issue an invitation.
- **No second factor.** Recommended for owners and platform administrators before public launch.
- **Enrolment has no phone verification** (SMS/OTP provider not chosen); see [loyalty-and-enrollment.md](loyalty-and-enrollment.md).
- Access tokens are HS256 with one shared secret; asymmetric keys and rotation are possible (`src/common/crypto/jwt-rs256.ts` exists) but not wired.
